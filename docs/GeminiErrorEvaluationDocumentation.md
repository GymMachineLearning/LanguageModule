# Feature: Gemini Video Error Classification Pipeline for MLPSD

## 1. Cel feature’u

Celem modułu jest zbudowanie pipeline’u w Pythonie, który:

1. Wczytuje listę nagrań przysiadów.
2. Dla każdego nagrania wysyła wideo do Gemini API.
3. Otrzymuje predykcję błędów technicznych w postaci przedziałów czasowych.
4. Waliduje odpowiedź modelu.
5. Konwertuje przedziały czasowe na binarne etykiety klatkowe `6 x T`.
6. Zapisuje wyniki w formatach `.json`, `.csv`, opcjonalnie `.npy` / `.npz`.
7. Liczy metryki względem ground truth MLPSD.
8. Generuje raport końcowy z wynikami.

Moduł ma być prototypem badawczym w Pythonie, niezależnym od aplikacji Android.

# 7. Ważna decyzja: File API vs inline video

Gemini pozwala przesyłać wideo jako File API, inline data lub YouTube URL. Dokumentacja rekomenduje File API dla większych plików, dłuższych nagrań i sytuacji, gdy plik ma być użyty w wielu zapytaniach .

Dla Twojego przypadku:

## Opcja A — File API

Dobra dla:

* większych plików,
* batcha 300 nagrań,
* stabilnego uploadu,
* możliwości ponownego użycia pliku przez 48 h.

Files API pozwala przechowywać do 20 GB plików na projekt, z limitem 2 GB na plik, a pliki są przechowywane przez 48 godzin .

Problem: przy File API dokumentacja mówi, że wideo są przechowywane z próbkowaniem 1 FPS, a timestampy są dodawane co sekundę; można nadpisać domyślne próbkowanie, ale trzeba to jawnie zaplanować i przetestować .

## Opcja B — inline video

Dobra dla:

* krótkich, małych nagrań,
* testów promptu,
* większej kontroli nad `video_metadata.fps`.

Dokumentacja pokazuje przykład inline video z `video_metadata=types.VideoMetadata(fps=5)`, czyli można wymusić większe próbkowanie dla zadań wymagających dokładniejszej analizy temporalnej .

# 14. Batch runner

## Wymagania

Batch runner powinien:

* obsługiwać 300 nagrań,
* zapisywać wynik po każdym nagraniu,
* umożliwiać wznowienie przerwanego runu,
* pomijać już przetworzone filmy,
* mieć retry z backoffem,
* logować błędy do `failures.csv`,
* nie tracić raw response z API.

# 21. Najważniejsze ryzyka

## 1. Zbyt niska rozdzielczość czasowa

Jeżeli Gemini analizuje wideo efektywnie przy 1 FPS, może wykryć błąd, ale źle określić początek i koniec. Dlatego metryki segmentowe muszą mieć tolerancję czasową.

## 2. Model może dobrze klasyfikować globalnie, ale słabo lokalizować

Dlatego osobno licz:

## 3. Prompt może wpływać na wyniki bardziej niż model

Traktuj `prompt_version` jak hiperparametr eksperymentu.

## 4. Model może zwracać fałszywie precyzyjne timestampy

Dlatego w JSON warto mieć `confidence`, a w analizie dodać metryki z tolerancją.

## 5. Structured output nie gwarantuje sensownych wartości

Gemini może zwrócić poprawny JSON, ale np. segment poza długością filmu. Dokumentacja wprost zaleca walidację wyników po stronie aplikacji mimo użycia structured output .

# 22. Moje pytania, które warto rozstrzygnąć przed kodowaniem

Mam tylko cztery pytania, ale możesz zacząć implementację bez odpowiedzi na nie:

1. Czy ground truth masz jako `.npy 6 x T`, czy w innym formacie?
2. Czy liczba klatek `T` w etykietach odpowiada surowemu FPS wideo, czy już przetworzonej sekwencji po preprocessingu?
3. Jak duże są pliki wideo: poniżej 20 MB czy większe?
4. Czy najważniejsza metryka dla pracy ma być frame-level F1, video-level F1, czy segment-level IoU?

Moja rekomendacja na start:  **zrób File API + structured JSON + konwersję sekund do `6 x T` + trzy poziomy metryk** . Potem dodaj wariant z wyższym FPS jako eksperyment, bo to może być najciekawszy wynik badawczy tego feature’u.
